## Engine recommendation and decision gate

**Recommend Konva/react-konva as the leading candidate for the existing React workspace, subject to the comparative spike.** Keep ONYX's document and commands authoritative; treat rendered nodes as a disposable projection. This recommendation is not an accepted dependency decision or measured performance result.

| Approach          | Fit for ONYX                                                                                                                                            | Costs and decision risks                                                                                                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Konva/react-konva | Declarative React scene graph; image/text nodes and pointer events fit the existing state-driven shell. A Transformer supplies resize/rotation handles. | Transformer attachment still needs node refs. Text editing needs a DOM input overlay, plus explicit Arabic shaping, caret, IME and export verification. Keep React document updates at completed gesture boundaries, with bounded transient rendering during movement. |
| Fabric.js         | Editing-oriented canvas, selection, object controls, editable text classes, stacking and serialization could reduce initial editing work.               | Imperative canvas state needs an adapter that avoids competing with React state. Native JSON is not the ONYX file format; text fidelity, object lifecycles and mobile performance still require the same experiments.                                                  |
| Custom SVG/DOM    | SVG has explicit viewBox/transforms; DOM inputs offer native editing and accessible controls. Attractive for a small constrained object set.            | ONYX would own selection, transform handles, hit testing, snapping, grouping, touch arbitration and export fidelity. Arbitrary DOM content is not a reliable print representation. Highest custom interaction burden for the planned feature set.                      |

These capability statements follow the primary [React integration](https://konvajs.org/docs/react/index.html), [Konva Transformer](https://konvajs.org/docs/react/Transformer.html), [Konva text-editing example](https://konvajs.org/docs/sandbox/Editable_Text.html), [Fabric core concepts](https://www.fabricjs.com/docs/core-concepts/) and [SVG coordinate model](https://www.w3.org/TR/SVG2/coords.html). The tradeoff judgments are ONYX recommendations.

[ADR 0002](../architecture/decisions/0002-canvas-engine.md) remains pending: its earlier Fabric-first hypothesis is not an accepted selection. Reuse the [comparative spike and hard gates](../spikes/canvas-evaluation.md), especially Arabic/Latin text, portable round trips, print isolation, keyboard access and real mobile interaction/memory. Compare the same fixtures, record exact package versions/licenses and React compatibility, then amend the ADR after evidence. Do not install both engines into the customer workspace merely to compare them.

Integrate the selected renderer behind one client-only `EditorSurface` boundary inside the existing workspace. Keep the server catalog read and shell intact. If browser-only loading needs `next/dynamic({ ssr: false })`, put that declaration in a Client Component, as required by the installed Next.js lazy-loading guide. Verify the selected binding against installed React 19.3.1 in a production build; do not assume minor-version compatibility from a library name.

## Document, assets and coordinates

Extend the current version-1 shell through an explicit migration to a proposed **schemaVersion 2**. Validate inputs at runtime as well as with TypeScript. Use this engine-independent structure:

| Record               | Proposed fields and invariant                                                                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Project              | `schemaVersion`, stable `id`, monotonic `revision`, `createdAt`, `updatedAt`, `catalogRevision`, `garment: { productId, variantId, sizeId: null or ID }`, `sides`, asset/font manifests and nullable `productionSpecRef`.       |
| Side document        | Independent `front` and `back`; a calibrated design-space reference, `objectsById`, and `layerOrder` from back to front. Every object appears exactly once in that side's order.                                                |
| Common object        | Stable `id`, `kind`, plain-text name, `visible`, `locked`, opacity, and transform `{ centerX, centerY, width, height, rotationDeg, flipX, flipY }`. Dimensions are finite and positive.                                         |
| Catalog artwork      | `kind: artwork`, catalog artwork ID/revision and asset ID. A rights snapshot supports provenance; current commercial approval must be rechecked before production.                                                              |
| Uploaded image       | `kind: image`, asset ID and explicit crop rectangle in source-image coordinates. Preserve original bytes and dimensions; thumbnails are separate derived assets.                                                                |
| Text                 | `kind: text`, Unicode content, font ID/version, font size, weight/style, line height, alignment, language/direction and fill. Preserve editable source text even if a later print adapter outlines glyphs.                      |
| Asset/font manifest  | Stable IDs, digest, MIME type, byte size, pixel dimensions where relevant, provenance and required font license information. References resolve to catalog assets or local Blobs, never expiring object URLs or engine objects. |
| Production reference | Supplier specification ID/revision, per-side print regions, calibration version and later production-option IDs. Null means production validation/export is unavailable.                                                        |

Follow the existing [document strategy](../architecture/design-documents.md): recommend **millimetres**, top-left origin per side, x right/y down, clockwise rotation about the object's center. RTL changes UI and text direction, never physical x/y or front/back identity. Normalize a renderer's scale into canonical dimensions at transform commit; define flip and crop composition once. Groups, if introduced, need an explicit versioned parent/child transform rule rather than silently flattening objects.

Actual printable dimensions and mockup registration are still unknown. Use clearly labelled synthetic geometry only for the engine spike. Do not derive millimetres from the 1774×887 PNG or present provisional dimensions as approved production data. Product/size changes must validate geometry and require an explicit fit decision if placement becomes invalid.

Keep camera `{zoom, x, y}`, Fit, device-pixel ratio, active side/view, selected IDs, current tool, panels, Pin and theme in workspace state. Neither camera movement nor theme changes create document history or unsaved edits. Pointer conversion uses the inverse of the camera transform and the calibrated design-to-preview transform; apply the camera once to the mockup and artwork together. Both view renders separate side documents; editing targets one explicit side.

Use plain ONYX data for persistence/history, consistent with [Konva's serialization guidance](https://konvajs.org/docs/data_and_serialization/Best_Practices.html). Migrating the empty version-1 shell preserves valid product/variant IDs and creates empty sides. Unknown newer schemas, missing assets or invalid numbers must fail without replacing current work.

## Interaction and history

Commands should cover place, transform, text edit, duplicate/delete, align, reorder, toggle visibility/lock and later group/multi-selection. Resolve catalog compatibility through existing selectors; inspecting artwork must remain distinct from adding it. Selection, outlines and guides are workspace overlays excluded from export. Locked objects cannot move through either gestures or keyboard actions.

Use a gesture transaction: pointerdown captures the starting state, pointermove updates transient geometry, pointerup validates and commits one undoable command. Escape/pointercancel/lost capture rolls back. Bound history by measured memory cost; immutable command patches or small snapshots reference assets rather than duplicating Blobs. A new edit after Undo discards the redo branch. Coalesce text input into deliberate edit transactions and preserve side identity in history entries.

Provide Delete, duplicate, arrows for nudging, a documented larger-step modifier, Escape, and platform-appropriate Undo/Redo. Ignore editor shortcuts while native text inputs or IME composition are active. Layers and numeric transform fields provide keyboard alternatives to canvas manipulation, with visible focus and localized selection announcements.

Preserve all five docks, side rails, resizing and universal Pin. In Select mode, one finger on a selected object manipulates it; Hand mode owns pan. Two-finger gestures own camera navigation: cancel/roll back an unfinished object drag before entering pinch, and do not resume it when one finger lifts. Empty-canvas navigation must have an explicit rule and never compete with object handles. Panel-body swipes remain native scrolling; only dedicated panel handles move/resize panels. Opening a tool must keep a useful portion of the garment visible. Test virtual keyboards, orientation changes and app background/return on real phones.

## Save/load lifecycle

Retain the confirmed **two automatic local project slots** and replacement consent rules in the [existing persistence design](../architecture/design-documents.md); do not silently evict a project when opening a third. Use IndexedDB for versioned documents and original Blob assets. Its transactional record model is documented by the [IndexedDB specification](https://www.w3.org/TR/IndexedDB/). localStorage remains suitable only for small workspace preferences.

Save a validated revision and its asset references atomically. Debounce completed edits, serialize pending writes, and mark “saved on this device” only after the transaction commits. If newer edits occur during a save, keep the newer revision dirty. Track saved revision separately from undo position. Do not rely on unload as the only save opportunity. Failed writes retain editable in-memory work and an honest unsaved state.

Load into staging: validate schema/budgets/digests, migrate a copy, resolve assets/fonts, then replace active state. Add revision checks and cross-tab notification to prevent silent lost writes. Handle quota denial, eviction, corrupted data and unavailable fonts explicitly; browser storage is not a backup guarantee. Garbage-collect only unreferenced Blobs after successful replacement. Validate the proposed portable `.onyx` package separately; it remains a transport proposal, not an implemented format.

## Print and pricing boundaries

Build an isolated print adapter from canonical **artwork objects only**, one output per side. Never export the live screen or depend on hiding UI before a screenshot. Mockup, environment/background, grid, ambient light, guides, handles and selection outlines are structurally outside the printable tree. Use originals and approved fonts; viewport size, zoom and device-pixel ratio must not alter output dimensions.

The [DTF contract](../printing/dtf-pipeline.md) already lists the unresolved supplier decisions: physical print regions and registration per product/size/side, safe area/bleed, target and minimum effective PPI, alpha handling, accepted format/color profile, font handling, white ink/mirroring responsibility and physical proof approval. Its 300 PPI example remains provisional. Export must remain unavailable as “print-ready” until those specifications and calibration are approved. Check source effective resolution, CORS-readable assets, licensed fonts and bounded encoding memory; an oversized canvas cannot add source detail.

The typed catalog already models products, variant activation/availability, separate front/back mockups, artwork categories/compatibility/rights, nullable display prices and nullable print specifications. `studioCatalog.getCatalog()` is the replacement boundary for future administration. Current fixtures supply only a black preview variant and artwork without commercial approval. No database or admin UI exists.

Future work must add runtime catalog validation, revisioned asset identity, size/stock rules, production-option schemas and authoritative price rules; current nullable display prices are not a pricing engine. A future quote takes product, size, color, printed sides, artwork/production options and rule revision. The server must validate the final order against current business rules. Do not invent prices, treat preview availability as stock, or use historical client quotes as authority.
