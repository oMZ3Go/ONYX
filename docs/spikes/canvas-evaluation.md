# Phase 02 specification — Fabric.js vs Konva/react-konva

Status: planned experiment, not executed. ADR 0002 remains pending. Objective: select a maintainable engine/adapter and text/export strategy using identical representative tasks. This is a bounded harness, not the full studio.

## Setup and reproducibility

Use one minimal Next.js shell with two isolated candidate routes, the same canonical fixture loader, assets, physical units and export inspector. Record package/React/browser/OS versions, licenses, bundle bytes, device CPU/RAM, viewport/DPR, and build command. Production build measurements only. Do not import both engines into storefront routes or commit either as the selected production dependency in Phase 00.

Suggested timebox: two engineering days per candidate plus one day for comparison; if a hard gate fails, document it before expanding scope. Record actual effort rather than infer maintenance cost from code line count. Test Windows Chrome/Edge, Android Chrome and actual Instagram/TikTok embedded browsers, and Safari on a real supported Apple mobile device. Select representative low/mid-tier Android hardware with owner input; emulator-only data cannot pass touch/memory gates. If hardware unavailable, mark the gate blocked, not passed.

Fixtures: 10/100/300 objects across both sides; groups/locked/rotated/nonuniformly scaled elements; transparent PNG/JPEG originals; small and large rasters; synthetic 300×350 mm area; licensed Arabic/Latin font files with known glyphs; malformed/oversized project fixtures. Record hashes so both engines use identical data. Synthetic dimensions and budgets below are **R**, never approved production constraints.

Distinguish cold-load cost, asset decode, interaction and encoding. `performance.now()` plus frame scheduling/traces measures interaction; record network separately. Avoid treating desktop heap APIs as portable across browsers.

## Rubric and decision

Hard failures disqualify the current strategy until fixed and retested. Score each category 0–5 with linked evidence: Arabic/text editing 25%, export/fidelity 20%, touch/accessibility 20%, editing/document fidelity 15%, performance/resource cost 10%, React/TypeScript/maintenance 10%. Weighted score = sum(weight × score / 5), out of 100. Suggested threshold 80 with every hard gate passed; within five points, prefer lower evidenced maintenance burden. Owner/technical lead review exceptions, never bury them in the mean score.

Deliverables: two runnable bounded harnesses, shared canonical fixtures, screenshots/videos/traces, measurement table, integration/cleanup notes, package/license/security review, documented known limitations and updated ADR with the recommendation. If both fail Arabic editing, evaluate DOM text-input overlay/font/layout strategy before changing the whole product. If mobile export fails, measure a bounded server adapter separately and document cost/deployment consequences.

Source starting points: [Fabric API/object and text controls](https://www.fabricjs.com/docs/), [react-konva integration](https://konvajs.org/docs/react/index.html), [Konva export](https://konvajs.org/docs/react/Canvas_Export.html). Library capability lists are hypotheses; none substitutes for ONYX fixtures or real device evidence.
